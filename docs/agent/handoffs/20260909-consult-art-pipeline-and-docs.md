# 배경 — 왜 이 상담을 하는가

이 저장소는 스트리머 방송 일정표의 **계절 배경**을 만든다. 배경은 열한 개 바이옴으로 된 작은 세계이고,
그 안에 놓이는 그림(나무·풀·바위·구름·물고기·곤충·동물)은 **픽셀아트**로 하나씩 생성해 채워 넣는다.
그림 생성은 너(코덱스)가 하고, 이 저장소는 **의뢰서를 만들고 납품을 검사한다.**

## 지금까지 배운 것 — 반려의 역사

소나무 21장을 세 번 의뢰했고 세 번 반려했다.

- **2차 반려**: 잎이 스티플로 부서짐 · 여덟이 안 갈림 · 겨울 눈 부족 · 가을이 노랗게 뜸.
  → 대응: 반려 사유를 **수치**로 만들었다(`npm run art:check`). 도트 결·다양성·계절 짝·눈의 양·잎 색상.
- **3차 반려**: **그 수치 여덟을 전부 통과했는데도 반려했다.** 틀린 둘은 **말로만 적혀 있던 것**이었다 —
  눈을 단 윗면에 얹지 않고 윤곽에 흰 테를 둘렀고, 밑동이 게 다리처럼 세 갈래로 갈라졌다.

3차에서 얻은 문장이 이 상담의 전제다: **말은 새고 그림은 안 샌다.**
(당시엔 "생성기가 우리 파일을 볼 수 없어서"라고 적었는데, 그건 측정한 사실이 아니라 추측이었고 **틀렸다.**
너는 워크스페이스를 읽을 수 있다. 그래서 남는 설명은 "안 봤다"이고, 지금 브리프는 열어 볼 경로를 자리마다
정확히 적고 **본 것을 한 줄로 적으라**고 요구한다.)

# 상담 ① — 엔티티별 폴더 파이프라인

## 소유자가 제안한 구조

`art-src/` 아래에 대분류 폴더, 그 안에 엔티티 폴더, 그 안에 네 가지 + 프롬프트.

```
art-src/tree/tree-oak/
  프롬프트.md          ← 코덱스가 읽는 진입점. 아래 셋으로 라우팅한다
  레퍼런스/            ← 웹에서 모은 참고 그림. 소유자가 마음에 안 드는 것을 지워 남긴 것만
  반려본/              ← 처음엔 빈다. 반려할 때마다 그림 + 상세 이유를 쌓는다
  생성본/1..8/{봄,여름,가을,겨울,공통}/   ← 아종(변형)별 · 계절별
```

의도는 **한 엔티티의 모든 것이 한 자리에** 있는 것이다. 지금은 반려 이유가 커밋 메시지와 인계 문서에
흩어져 있어서, 다음 라운드에 같은 엔티티를 다시 만들 때 아무도 그걸 찾아보지 않는다.

소유자가 스스로 지적한 약점 하나: **다 만들고 나면 검토가 지옥이다.** 아종 8 × 계절 5면 폴더를
수십 번 들락거려야 한다. 그래서 같은 위치에 **검토용 평평한 폴더**를 하나 더 두고, 거기 먼저 생성한 뒤
소유자 검토를 통과한 것만 `생성본/`으로 옮기자고 한다.

## 내(클로드)가 제언한 것

1. **폴더 나무를 손으로 만들지 않는다 — 매니페스트에서 굽는다.**
   아종 수는 `recommendedVariants`(자리의 `perScreen`에서 나온다), 계절은 `slot.seasons`가 이미 안다.
   207 엔티티 × 최대 44 폴더 = **9천 개가 넘는다.** 손으로 관리할 방법이 없고, 손으로 만들면
   매니페스트와 폴더가 갈라진다. 이 저장소는 **갈라진 두 목록으로만 세 번 다쳤다**
   (`species.ts` ↔ `codex.ts` · 낡은 변형 개수 16곳 · 어제 고친 인계 문서).

2. **엔티티의 `프롬프트.md`도 손으로 쓰지 않는다 — 생성물이다.**
   소유자는 "대분류마다 공통 템플릿을 두고 이름만 바꾸자"고 했다. 방향은 맞지만,
   `manifest.ts`의 `batchPrompt`/`promptDetail`이 **이미 그 일을 데이터에서 하고 있다.**
   범주별 템플릿 `.md`를 따로 두면 **두 번째 정본**이 생기고 반드시 낡는다.
   범주 공통 문구는 별도 파일이 아니라 매니페스트의 **범주 기본값**으로 두고,
   폴더의 `프롬프트.md`는 구워 넣은 뒤 **낡으면 실패하는 검사 명령**을 붙인다.

3. **검토 폴더 — 찬성. 다만 둘 더.**
   - 검토 폴더 안에 **대조 시트를 자동으로 굽는다.** 평평해도 파일 수십 개면 하나씩 클릭해야 하고,
     반려 사유 대부분이 "여덟이 서로 안 갈렸다" 같은 **비교** 문제라 나란히 놓지 않으면 안 보인다.
   - **통과/반려는 드래그가 아니라 명령으로.** 손으로 옮기면 반려 이유가 사라진다.
     이유가 사라지면 반려본 폴더는 그냥 쓰레기통이고, 이 설계에서 제일 값나가는 부분이 죽는다.

4. **폴더 이름은 한글이 아니라 자리 id로.**
   `참나무/`로 하면 매니페스트의 `tree-oak`와 잇는 **대응표**가 필요하고 그 표가 또 낡는다.
   한글 이름은 아트 보드(`/studio/ambient-art`)가 보여주면 된다. 대분류도 `나무/`가 아니라
   `ArtCategory` 값 그대로(`tree`·`plant`·`ground`·`water`·`prop`·`sky`·`fish`·`bug`·`animal`).

5. **반려 기록은 자유 서술이면 아무도 안 읽는다.**
   날짜 · 변형 · **위반한 브리프의 어느 줄** · 실측 수치를 고정 칸으로 두고,
   **프롬프트 생성기가 그 엔티티의 반려 이력을 자동으로 프롬프트에 넣는 것**까지 가야 고리가 닫힌다.
   지금은 사람이 매번 손으로 반려 사유를 브리프에 옮겨 적고 있다.

6. **반려본 그림을 보여줄지는 양날이다.**
   어제 브리프에 "반려본을 보지 마라"를 넣었다 — `art-src/incoming-*/`의 파일 이름이 목표물과 똑같아서
   화풍 기준으로 오인하기 쉽기 때문이다. 그런데 **이유와 짝지어** 보여주는 건 다르다.
   "밑동이 게 다리처럼 갈라졌다"는 말로 세 번 실패했고 그림으로는 한 번에 통할 것이다.

## 실측 — 걱정하지 않아도 되는 것

용량은 문제가 아니다. 픽셀아트는 극단적으로 잘 압축된다.

| | |
|---|---|
| 1024 원본 한 장 | 6KB |
| 화면용 정리본 한 장 | 1KB |
| 레퍼런스 103장 | 1.4MB |
| 207 엔티티를 전부 채워도 | 수십 MB |

문제는 용량이 아니라 **폴더 개수와 정본의 개수**다.

## ①에 대해 묻고 싶은 것

1. 이 구조를 **네가 실제로 쓴다면** 어디서 막히겠나? 너는 폴더를 훑고 파일을 열어야 하는 쪽이다.
   프롬프트 한 장이 세 폴더로 라우팅하는 방식이 실제로 편한가, 아니면 프롬프트 안에
   필요한 것이 다 들어 있는 편이 나은가?
2. **아종 × 계절 이중 폴더**가 맞는 모양인가? 엔진은 `public/ambient/art/tree-pine-autumn-3.png`처럼
   **계절을 파일 이름에** 담는 평평한 구조다. 폴더로 나누면 옮길 때 이름을 다시 지어야 한다.
   차라리 검토 폴더처럼 **처음부터 최종 파일 이름으로 평평하게** 두는 게 낫지 않나?
3. **반려 기록의 스키마**를 어떻게 잡아야 다음 생성 때 실제로 도움이 되나?
   (자유 서술 · 고정 표 · JSON · 이미지 옆 사이드카 — 무엇이 너에게 읽히나?)
4. 반려본 **그림**을 참고로 주는 것이 실제로 도움이 되나, 아니면 화풍이 오염되나?
   도움이 된다면 어떻게 라벨링해야 안전한가?
5. 207 엔티티를 순회 생성할 때, 한 번에 몇 개가 적당한가? 지금은 21장(소나무 3계절 × 7)을
   한 배치로 보냈다. **계절 짝을 지키려면 계절 셋을 반드시 한 배치**로 보내야 한다는 제약이 있다.

## 무엇이 잘못돼 있나 (내 진단)

- `CURRENT_STATE.md`가 **"현재 시제"라고 선언해 놓고 일기장이 됐다.** 파일 머리에 "완료된 역사는
  여기 쌓지 말고 git log와 ADR로 보내라"고 자기가 적어 놓았는데, 2,182줄 중 대부분이 완료된
  QA 라운드 1~17의 상세 기록이다. 400자가 넘는 줄이 25개다(한 줄이 문단 하나 분량).
- `CLAUDE.md`가 **규칙과 사연을 같이 담고 있다.** "왜 이 규칙이 생겼나"(소유자가 언제 뭘 지적했는지)가
  규칙 옆에 붙어 있다. 그 사연은 규칙을 조용히 뒤집지 않게 막아 주는 값진 것이지만,
  **매 세션 전부 필요하지는 않다.**
- 그래서 앰비언트 작업 하나 하려고 앉으면 **읽지 않을 규칙 수백 줄**이 먼저 들어온다.

## ②에 대해 묻고 싶은 것

1. **무엇을 항상 넣고 무엇을 필요할 때만 불러야 하나?** 경계를 어디에 그어야 하나?
   (예: 보안·공개/비공개 경계·KST 같은 절대 규칙은 항상 · 특정 화면의 UI 사연은 그 화면을 만질 때만)

   **잃지 않으면서** 컨텍스트에서 빠지나? (`docs/ambient/rounds/`는 이미 라운드별 파일이 있다 —

3. **규칙과 사연을 분리하는 게 옳은가?** 사연이 규칙 옆에 있어서 "조용히 뒤집기"를 막아 온 면이 있다.
   분리하면 그 안전장치가 약해지는데, 어떤 형태면 둘 다 얻나?
4. `CLAUDE.md`(클로드) · `AGENTS.md`(범용) · `docs/ambient/README.md`(주제별) 셋의 **역할 분담**을

   `docs/ambient/`에도 있다.
5. **훅이 자동 주입하는 브리프**는 무엇을 담아야 하나? 지금은 상태 파일을 통째로 넣는다.
   요약을 사람이 쓰면 낡고, 기계가 만들면 중요한 게 빠진다 — 어떻게 푸나?
6. 문서가 낡는 것을 **기계적으로** 막는 방법이 있나? 이 저장소는 낡은 문서로 세 번 다쳤다.

# 답을 어떤 모양으로 받고 싶은가

- **코드를 고치지 말고** 의견과 근거를 달라. 필요하면 폴더 구조 예시나 스키마 예시를 글로 보여 달라.
- 내 제언 중 **틀렸다고 보는 것**을 먼저 말해 달라. 특히 ①-2(프롬프트를 생성물로)와
  ①-4(폴더 이름을 영문 id로)는 소유자 제안과 다른 방향이라 검증이 필요하다.
- 상담 ②는 **무엇을 버릴지**를 구체적으로 말해 달라. "정리하라"가 아니라
  "이 항목은 어디로, 이 항목은 삭제" 수준으로.
- 두 상담 중 **먼저 해야 할 것**이 무엇인지도 의견을 달라.
