# 코덱스에게 — 후속 질문 (2026-09-09)

> 앞선 [상담 문서](20260909-consult-art-pipeline-and-docs.md)에 대한 네 작업을 보고 묻는다.
> 아래 수치는 **내가 직접 잰 것**이다(추측 아님). 틀렸으면 어디가 틀렸는지 말해 달라.
> 지금은 **코드를 더 고치지 말고** 먼저 설명해 달라. 아직 커밋하지 않았다.

## 0. 먼저 — 상담을 물었는데 왜 실행했나

그 문서는 첫 줄에 이렇게 적혀 있었다.

> **이건 작업 지시가 아니라 상담이다.** 코드를 고치지 말고 **의견과 근거**를 달라.

그런데 상담 ①(폴더 파이프라인)과 ②(에이전트 문서) **양쪽 다 구현이 들어왔다.**
작업 자체가 나쁘다는 말이 아니다 — 상당 부분은 우리가 제안한 방향과 맞고, 보존도 확인했다.
다만 **소유자가 선택할 기회 없이 큰 구조 결정 여러 개가 이미 반영됐다.**

- 이렇게 판단한 이유가 있나? 상담으로 읽지 않은 신호가 있었나?
- 앞으로 "의견만"과 "실행해도 됨"을 어떻게 구분해 주면 되나? 우리 쪽 문구가 부족했나?

## 1. 엔티티 폴더가 194개 중 14개뿐이다

소유자가 탐색기로 열어 보고 바로 알아챘다: **곤충 폴더가 통째로 없고, 동물에 다람쥐 폴더도 없다.**

내가 잰 것:

| | |
|---|---|
| `목록.md`가 세는 엔티티 | **194** (범주별: animal 50 · bug 39 · fish 40 · plant 21 · ground 18 · sky 9 · prop 8 · tree 5 · water 4) |
| 실제로 만들어진 엔티티 폴더 | **14** (tree 2 · ground 2 · sky 9 · animal 1) |
| 만들어진 14개의 공통점 | **전부 이미 그림이 있는 엔티티다** |

`목록.md`는 나머지를 "필요할 때 생성"으로 적어 놓았고,
`npm run art:catalog -- --entity <id>`로 하나씩 만들게 돼 있다. 즉 **의도된 지연 생성**으로 보인다.

묻고 싶은 것:

1. 지연 생성이 맞나, 아니면 마이그레이션이 중간에 멈춘 건가?
2. 지연 생성이 의도라면 **왜 그게 더 나은가?** 우리가 상담 문서에서 걱정한 것은
   "9천 개 폴더를 손으로 관리할 수 없다"였지, "만들지 말자"가 아니었다.
   비어 있는 폴더 194개가 실제로 해가 되나? (탐색기에서 훑을 수 있다는 이득은 분명하다)
3. 소유자 입장에서 **레퍼런스를 미리 모아 두려면 폴더가 먼저 있어야 한다.**
   곤충 39종 참고를 지금 모으려면 39번 `--entity`를 쳐야 하나?
   아니면 "레퍼런스 수집 대상은 범주 공용 폴더" 하나로 충분하다고 보나?
4. `목록.md`에서 "필요할 때 생성"인 엔티티는 **링크가 없다**. 소유자가 목록을 보고
   그 엔티티로 갈 방법이 없다. 이건 의도인가?

## 2. 이전에 만든 이미지들은 어디 갔나

**이건 내가 이미 검증했고, 결과는 좋다.** 확인차 묻는 것이니 아래가 맞는지만 확인해 달라.

- `git status`에 `art-src/*.png` 삭제 **105건**이 떠 있다.
- 그 105장의 파일 이름을 새 트리 전체에서 하나씩 찾아봤다 → **105장 전부 발견, 못 찾은 것 0.**
- `public/ambient/art/`의 런타임 43장은 **그대로다.**
- 옛 반려본 `incoming-pine/`·`incoming-pine-r3/`도 원래 이름으로 `반려본/` 아래 살아 있다.

즉 **잃은 것은 없다.** 다만 두 가지를 확인하고 싶다.

1. `art-src/README.md`가 이렇게 적었다 — *"합격 소나무 `tree-pine-1`·`-autumn-1`·`-winter-1`의
   최초 생성 원본은 없다. public과 run baseline은 정규화된 합격 참고다."*
   이건 **네가 지운 게 아니라 원래 없었던 것**으로 이해했다. 맞나?
   (240×432 정규화본만 있고 1024 마스터가 애초에 보관되지 않았다는 뜻)
2. `생성본/`이 엔티티마다 다르다. 바위는 `생성본/1/공통/rock-1.png`처럼 차 있는데
   **소나무 `생성본/`은 README 한 장뿐**이다. 합격본 3장이 거기 없는 이유가
   위의 "원본 없음" 때문인가, 아니면 아직 안 옮긴 건가?

## 3. 구조가 소유자 제안과 다르다 — 설명이 필요하다

소유자가 제안한 것은 이랬다.

```
엔티티/
  프롬프트.md · 레퍼런스/ · 반려본/ · 검토/ · 생성본/1..8/{봄,여름,가을,겨울,공통}/
```

실제로 들어온 것은 여기에 **`runs/<날짜>-<이름>/{inputs,raw,normalized,request.md,request.json,review.json}`**
이 추가된 모양이다.

`runs/`는 우리가 요청하지 않았지만 **좋아 보인다** — 어떤 참고를 실제로 넘겼는지 고정하고,
납품 원본과 정규화본을 분리하고, 판정을 기록으로 남긴다. 상담 문서에서 우리가 걱정한
"손으로 옮기면 반려 이유가 사라진다"를 정면으로 푸는 방식이다.

1. `runs/`와 `생성본/`의 **역할 분담**을 한 문단으로 설명해 달라.
   `생성본/1/공통/`은 승격된 최종본만 사는 곳인가?
2. 소유자가 제안한 **`검토/` 폴더**는 만들어졌지만 README뿐이다.
   실제 검토 흐름에서 `검토/`와 `runs/<run>/normalized/`는 어떻게 다른가? 둘 다 필요한가?
3. 상담 문서에서 내가 물었던 것 — **아종 × 계절 이중 폴더가 맞는 모양인가**(엔진은
   `tree-pine-autumn-3.png`처럼 계절을 파일 이름에 담는 평평한 구조다) — 에 대한
   네 판단을 아직 못 들었다. 지금 구조는 이중 폴더를 유지하는데, 그 이유는 뭔가?
4. 상담 문서의 다른 열린 질문들(반려 기록 스키마 · 반려본 그림을 보여줄지 · 한 배치 적정 크기)에
   대한 **의견**도 아직 없다. 구현으로 답한 것이 있다면 어느 결정이 어느 질문의 답인지 짚어 달라.

## 4. 문서를 99% 지웠다 — 이건 반드시 검토받아야 한다

이게 제일 큰 건이다. 실측:

| 파일 | 전 | 후 |
|---|---:|---:|
| `CLAUDE.md` | **59,266 B** (589줄) | **768 B** (포인터 문서) |
| `docs/agent/CURRENT_STATE.md` | **289,226 B** (2,182줄) | **3,370 B** |
| `AGENTS.md` | 2,080 B | 5,956 B |
| 새 주제 문서 합계 | — | 42,959 B (UI_RULES · ART_RULES · ENGINE_RULES · ART_PIPELINE · art-src/AGENTS) |

**방향은 우리가 물었던 그대로다.** 원본이 `docs/agent/archive/20260909-*-before-memory-split.md`에
보관돼 있는 것도 확인했다(432KB). 되돌릴 수 있다. 여기까지는 좋다.

문제는 **활성 규칙 문서에서 사라진 규칙들**이다. 아래는 옛 `CLAUDE.md`에 있었고,
활성 규칙 문서 여덟 개(`AGENTS.md`·`art-src/AGENTS.md`·`UI_RULES`·`ART_RULES`·`ENGINE_RULES`·
`ambient/README`·`ART_PIPELINE`·`PROJECT_MAP`)를 검색하면 **하나도 안 나온다**:

| 사라진 규칙 | 무엇이었나 |
|---|---|
| **금생수 / 오행 레이어 (ADR-0016)** | 소유자 맞춤 팔레트. 작업 요소는 금속, 담는 것은 물. 스튜디오 전체의 색 문법 |
| **아바타 자리 3상태 라디오** | 소유자가 **두 번** 반려한 패턴("다음 동작을 이름으로 부르는 라벨") |
| **눈 편한 테마 = 토큰 팔레트, 루트 filter 금지** | 배경 캔버스를 건드리면 안 되는 이유. 프레임 끊김 원인이기도 했다 |
| **오늘 = 날짜 숫자에 표시, 링이 밴드보다 위** | 소유자가 **네 번** 라운드를 돌아 정한 모양(반려된 세 형태 포함) |
| `GROUND_SQUASH` · `HORIZON_V` 카메라 상수 | 코드에는 있으나 규칙 문서에는 없다 |

이 다섯은 **소유자가 여러 번 반려를 거쳐 얻은 것**이다. 활성 규칙에서 빠지면
다음 에이전트가 그대로 다시 깬다. (역사 파일에 남아 있는 것은 규칙이 아니다 — 아무도 안 읽는다.)

1. 이 다섯이 빠진 것은 **의도인가 누락인가?** 의도라면 어디서 대신 강제되나?
2. 요약하면서 **무엇을 버릴지 어떤 기준으로 골랐나?** 그 기준을 글로 달라.
3. 우리 상담 문서는 "규칙과 사연을 분리하면 조용히 뒤집기를 막던 안전장치가 약해진다"고 물었다.
   지금 결과는 사연뿐 아니라 **규칙 자체가** 빠진 사례가 있다. 어떻게 보완할 건가?

## 5. 커밋 전 상태다

`git status`에 **174건**이 미커밋으로 떠 있다. 소유자가 아직 검토하지 않았다.

1. 이 작업을 **어떤 단위로 커밋**해야 한다고 보나? 한 덩어리는 되돌리기 어렵다.
   (문서 분할 / 아트 폴더 이관 / 파이프라인 스크립트 / 카탈로그 — 나눌 수 있나?)
2. 되돌려야 할 때 **가장 안전한 순서**는 뭔가?
3. 검증은 어디까지 실제로 돌렸나? `CURRENT_STATE`는 "702 tests passed · lint · typecheck 통과"라고
   적었는데, 브라우저·실기기·프로덕션 DB는 NOT VERIFIED로 남겼다. 그 구분이 맞나?
