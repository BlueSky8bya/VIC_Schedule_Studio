# 권한별 UI/UX 감사 및 벤치마크 보고서

작성일: 2026-05-28  
프로젝트: VIC Schedule Studio  
범위: 역할별로 실제 노출되는 버튼과 기능, 권한별 사용 흐름, 권한별 UI/UX 개선 전략을 읽기 전용으로 조사.

## 요약

VIC Schedule Studio의 서버 권한 모델은 이미 꽤 탄탄하다. 일정 편집, 비공개 레이어 조회, 포스터 꾸미기, 공개 시청자 경험이 `canEditSchedule`, `canDecorate`, `canReadPrivateLayer`, `canReadOwnerPrivate`로 분리되어 있다. 문제는 권한 로직 자체라기보다, UI가 "기능별 작업 흐름"이 아니라 "권한 조건에 맞는 버튼들을 한 줄로 나열한 구조"에 가깝다는 점이다.

추천 방향은 UI를 다음 기능군으로 재구성하는 것이다.

* **계정/모드 영역**: 역할 배지, 계정 변경, 비공개 레이어 토글, 시청자 미리보기.
* **일정 운영 영역**: 일정 추가/수정/삭제/정렬, 공지 작성, 태그.
* **접근/팀 관리 영역**: 비공개 비밀번호, 멤버 관리, 잠금 해제 상태.
* **포스터/꾸미기 영역**: 꾸미기 라우트, 스티커 도구, 업로드, 내보내기, 테마.
* **개발자 진단 영역**: 접속자 현황과 시스템 전용 정보.

이렇게 바꾸면 보안 경계는 그대로 유지하면서도, 각 역할이 "제한된 사용자"가 아니라 "자신에게 맞는 업무 화면을 받는 사용자"처럼 느껴진다.

## 현재 권한 모델

기준 파일:

* `lib/domain/schedule-types.ts`: `developer`, `owner`, `manager`, `worker`, `viewer` 역할 정의.
* `lib/permissions/roles.ts`: 핵심 권한 규칙.
* `components/studio/studio-shell.tsx`: 메인 스튜디오 UI 조건부 렌더링.
* `components/poster/public-poster.tsx`: 공개 포스터와 꾸미기 모드 조건부 렌더링.
* `lib/schedules/*-actions.ts`, `lib/private-layer/actions.ts`, `lib/trusted-members/actions.ts`: 서버 액션 권한 검증.

현재 역할 규칙:

* **개발자**: 일정, 태그, 멤버, 비공개 비밀번호, 스티커, 이미지 자료, 업도움 설정을 수정할 수 있다. 개발자 접속 현황 패널을 열 수 있다. 다만 "소유자만 보는 일정"은 만들거나 볼 수 없다.
* **소유자**: 일정, 태그, 멤버, 비공개 비밀번호, 스티커, 이미지 자료, 포스터 테마, 업도움 설정을 수정할 수 있다. 비공개 레이어 잠금 해제가 가능하고 소유자만 보는 일정을 읽고 만들 수 있다.
* **매니저**: 일반 일정, 태그, 멤버, 비밀번호는 수정할 수 없다. 방송 운영을 돕는 역할로, 공개 전/작업용 일정 확인, 업도움 기간/링크 수정, 포스터 꾸미기, 꾸미기 화면 내보내기를 맡는다.
* **작업자**: 일반 일정, 태그, 멤버, 비밀번호, 업도움 기간/링크는 수정할 수 없다. 버츄얼 의상, 그림, 이미지 자료, 스티커, 포스터 꾸미기처럼 제작물과 시각 자료 중심의 작업을 맡는다.
* **일반 시청자**: 공개 포스터만 본다. 월 이동, 공개 태그 필터, 일정 목록 보기, 업도움 링크, 좋아요/저장 같은 공개 상호작용을 사용할 수 있다. 스튜디오 비공개 데이터와 편집 도구에는 접근할 수 없다.

## 역할별 현재 UI/기능 인벤토리

### 개발자

현재 보이거나 사용할 수 있는 것:

* 스튜디오 상단 역할 배지.
* 비공개 레이어 토글. 잠금 해제 세션이 없으면 비밀번호 모달을 연다.
* 시청자 화면 미리보기.
* 계정 변경/logout.
* 개발자 세션 안내 영역.
* 태그 편집 모달.
* 멤버 관리 모달.
* 개발자 접속자 현황 패널.
* 달력 꾸미기 라우트 링크.
* 일정 선택, 생성, 수정, 삭제, 드래그 정렬, 연결 체인 조작.
* 일정 저장 버튼, 공개 범위 선택, 태그 선택, 업도움 편집, 공지 작성.
* 비공개 비밀번호 변경.
* 포스터 꾸미기 도구: 실행 취소/다시 실행, 기본 이모지, 텍스트 스티커, 이미지 업로드, 스티커 편집, 복제/삭제, 내보내기.
* `canEditSchedule` 역할이므로 포스터 테마 변경도 가능하다.

중요한 예외:

* 개발자는 편집 권한이 있지만 "소유자만 보는 일정"은 사용할 수 없다. 화면도 소유자에게만 해당 선택지를 보여준다.

UX 문제:

* 개발자 도구가 소유자 도구와 거의 같은 줄에 섞여 있다. 개발자는 운영상 강한 권한을 가진 유지보수자이므로, 일반 운영자 화면이 아니라 "시스템 유지보수 모드"처럼 분리되어 보여야 한다.

### 소유자

현재 보이거나 사용할 수 있는 것:

* 스튜디오 상단 역할 배지.
* 비공개 레이어 토글 및 잠금 해제 후 비공개 경고 배너.
* 시청자 화면 미리보기.
* 계정 변경/logout.
* 태그 편집 모달.
* 멤버 관리 모달.
* 달력 꾸미기 라우트 링크.
* 전체 일정 생성, 수정, 삭제, 드래그 정렬, 연결 체인 조작.
* 일정 저장 버튼, 소유자 전용을 포함한 공개 범위 선택, 태그 선택, 업도움 편집, 공지 작성.
* 비공개 비밀번호 설정/변경.
* 포스터 꾸미기 도구, 이미지 업로드, 스티커 편집, 내보내기, 포스터 테마 변경.

UX 문제:

* 소유자는 일상 운영의 중심 역할인데, 현재 상단 버튼 줄에서는 관리 기능, 꾸미기, 비공개 레이어, 시청자 미리보기, 계정 변경이 비슷한 무게로 나열된다. 소유자에게는 일정 운영을 가장 먼저 보이게 하고, 관리 기능은 따로 묶은 "발행 작업대"가 필요하다.

### 매니저

현재 보이거나 사용할 수 있는 것:

* 스튜디오 상단 역할 배지.
* 비공개 일정 보기 버튼과 잠금 해제 창. 잠금 해제 후에는 "공개 전 일정"과 "작업용 일정"은 볼 수 있지만, "소유자만 보는 일정"은 볼 수 없다.
* 시청자 화면 미리보기.
* 계정 변경/logout.
* 달력 꾸미기 라우트 링크.
* 꾸미기 화면에서 스티커 편집, 실행 취소/다시 실행, 스티커 복제/삭제, 내보내기.
* 기존 업도움 막대를 클릭하면 업도움 기간과 링크만 고칠 수 있는 작은 편집 창이 열린다.
* 공개 support 링크는 계속 사용할 수 있다.

숨겨지거나 차단되는 것:

* 태그 편집.
* 멤버 관리.
* 개발자 패널.
* 일반 일정 생성/수정/삭제/정렬.
* "소유자만 보는 일정".
* 포스터 테마 변경.
* 버츄얼 의상/아트 자료처럼 작업자용 제작 자료 관리.

UX 문제:

* 매니저는 방송 운영을 돕는 사람이다. 화면도 "방송 일정이 어떻게 공개될지 확인하고, 업도움 링크를 고치고, 포스터를 정리하는 사람"처럼 보여야 한다.

### 작업자

현재 보이거나 사용할 수 있는 것:

* 스튜디오 상단 역할 배지.
* 비공개 일정 보기 버튼과 잠금 해제 창. 잠금 해제 후에는 "공개 전 일정"과 "작업용 일정"은 볼 수 있지만, "소유자만 보는 일정"은 볼 수 없다.
* 시청자 화면 미리보기.
* 계정 변경/logout.
* 달력 꾸미기 라우트 링크.
* 꾸미기 화면에서 스티커 편집, 이미지 업로드, 이미지 삭제, 실행 취소/다시 실행, 스티커 복제/삭제, 내보내기.
* 작업에 필요한 공개 전/작업용 일정 확인.

숨겨지거나 차단되는 것:

* 태그 편집.
* 멤버 관리.
* 개발자 패널.
* 일반 일정 생성/수정/삭제/정렬.
* 업도움 기간/링크 수정.
* "소유자만 보는 일정".
* 포스터 테마 변경.

UX 문제:

* 작업자는 방송 채팅을 관리하는 사람이 아니라, 빅토리님과 함께 제작물을 만드는 협업자에 가깝다. 따라서 업도움 링크 수정 같은 방송 운영 기능보다, 참고 일정 확인, 자료 업로드, 꾸미기, 제작 상태 공유가 더 어울린다.

### 일반 시청자

현재 보이거나 사용할 수 있는 것:

* 공개 포스터.
* 월 이동.
* 공개 태그 필터와 agenda 모드.
* 이벤트 좋아요/저장.
* 업도움 링크.
* 상황에 따른 로그인/계정 변경 버튼.

숨겨지거나 차단되는 것:

* 스튜디오 편집 도구.
* 비공개 레이어 토글.
* 비공개 데이터.
* 꾸미기 도구.
* 일반 공개 화면의 내보내기 도구.
* 태그/멤버/개발자/관리 도구.

UX 문제:

* 시청자 모드는 귀엽고 깨끗한 포스터 중심 경험이어야 한다. 계정/로그인 버튼은 포스터보다 강하게 보여서는 안 된다. 시청자는 권한 구조를 이해하는 것이 아니라 공개 일정을 보고 반응하면 된다.

## 발견된 권한/UI 불일치

### 멤버 관리 권한

* 멤버 관리 모달은 소유자와 개발자를 허용한다.
* 별도 멤버 관리 페이지는 소유자가 아니면 입력칸과 등록 버튼이 꺼진다.

권장:

* 개발자가 멤버 관리를 해도 되는지 제품 정책을 명확히 정해야 한다. 허용한다면 두 화면 모두 개발자에게 같은 방식으로 열어준다. 허용하지 않는다면 두 화면 모두 소유자 전용으로 맞춘다.

### 개발자의 소유자 전용 일정 처리

* 개발자는 대부분의 일정 유지보수는 가능하지만, 소유자만 보는 일정은 읽거나 만들 수 없다.
* 이 규칙은 보안상 좋다. 다만 개발자는 프로젝트 구조를 아는 사람이라 장황한 안내 문구를 따로 붙일 필요는 낮다.

권장:

* 개발자 화면에는 소유자 전용 선택지를 조용히 숨긴다.
* 설명이 필요하다면 긴 문장 대신 짧은 도움말 정도만 둔다. 예: "소유자 전용 일정은 소유자에게만 표시됩니다."
* 이 안내는 개발자보다 매니저/작업자처럼 권한 차이를 헷갈릴 수 있는 사람에게 더 중요하다.

### 매니저/작업자의 일정 상세 화면

* 매니저/작업자가 일정을 눌렀을 때 소유자용 편집 화면이 열리면, 대부분의 칸이 고칠 수 없는 상태로 보일 수 있다.
* 일반 사용자는 "왜 눌렀는데 못 고치지?"라고 느낄 수 있다.

권장:

* 매니저와 작업자에게는 소유자용 편집 화면을 보여주지 않는다.
* 대신 일정 제목, 날짜, 공개 상태, 링크를 읽기 쉽게 보여주는 "일정 상세 보기"를 연다.
* 매니저가 업도움 일정을 볼 때만 "업도움 기간/링크 수정" 버튼을 가장 잘 보이는 위치에 둔다.
* 작업자가 업도움 일정을 볼 때는 수정 버튼 대신 "참고용 일정"처럼 보이게 한다.
* 즉, 매니저는 방송 운영을 고칠 수 있고, 작업자는 제작에 필요한 일정을 확인하고 자료를 다룰 수 있게 느껴져야 한다.

## 벤치마크 분석

### YouTube / Twitch / TikTok LIVE: 방송 매니저는 커뮤니티 안전 역할

YouTube는 라이브 채팅 매니저를 "커뮤니티가 안전하고 긍정적인 경험을 하도록 돕는 사람"으로 설명하고, 일반 매니저와 관리 매니저를 나눈다. Twitch도 매니저를 채팅을 안전하고 즐겁게 관리하는 역할로 설명한다. TikTok LIVE Studio 역시 매니저를 댓글 관리, 위반 방지, 참여 개선을 돕는 역할로 설명한다.

출처:

* YouTube Live chat moderators: https://support.google.com/youtube/answer/9826490
* Twitch Managing Roles: https://help.twitch.tv/s/article/Managing-Roles-for-your-Channel
* TikTok LIVE moderators: https://www.tiktok.com/live/studio/help/article/Boost-viewer-engagement/Add-moderators-to-manage-LIVE-chat-comments

VIC 적용:

* 매니저는 방송 운영과 커뮤니티 흐름을 돕는 사람으로 잡는 것이 자연스럽다.
* 매니저에게 어울리는 기능은 업도움 기간/링크 수정, 공개 전 일정 확인, 공지 초안 확인, 시청자 화면 점검, 방송 관련 링크 점검이다.
* 매니저에게 의상/이미지 제작 자료 관리까지 크게 열어두면 역할이 흐려진다.

### Patreon / Creator Team: 작업자는 제작 운영을 돕는 팀원

Patreon Team Accounts는 creator가 팀원을 초대해 창작 페이지 운영을 돕게 하는 구조다. Team Lead는 수익, 지급, 팀원 권한 같은 민감 영역을 독점하고, teammate는 혜택, 메시지, 페이지 개선, 콘텐츠 운영처럼 맡은 책임을 수행한다. 중요한 점은 팀원이 주인 계정을 공유하지 않고 자기 계정으로 자기 책임만 수행한다는 것이다.

출처:

* Patreon Team Account: https://support.patreon.com/hc/articles/360026751812
* Patreon Teammate permissions: https://support.patreon.com/hc/en-us/articles/360027997231-Teammate-permissions

VIC 적용:

* 작업자는 방송 채팅 매니저가 아니라 제작 협업자다.
* 작업자에게 어울리는 기능은 작업용 일정 확인, 의상/이미지/스티커 자료 업로드, 포스터 꾸미기, 제작 메모 확인, 결과물 상태 표시다.
* 작업자에게 업도움 링크 수정 권한은 빼는 것이 역할에 더 맞다.
* 작업자는 소유자 계정을 빌리는 사람이 아니라, 자기 계정으로 제한된 제작 업무만 하는 사람이어야 한다.

### Discord: 역할별 공간 분리

Discord는 역할과 채널 권한을 조합해 특정 역할만 접근할 수 있는 공간을 만들 수 있다. 역할 색상과 역할 계층도 구성원에게 "이 사람이 어떤 권한을 가진 사람인지"를 빠르게 알려준다.

출처: https://support.discord.com/hc/en-us/articles/214836687-Discord-Roles-and-Permissions

VIC 적용:

* 매니저와 작업자는 같은 화면에 버튼 몇 개만 다르게 보여주는 것보다, 각자 맡은 영역을 분리해 보여주는 편이 이해하기 쉽다.
* 매니저 화면은 방송 운영 중심, 작업자 화면은 제작 자료 중심으로 분리한다.
* 역할 배지도 "매니저"와 "작업자"가 색과 설명에서 확실히 달라야 한다.

### Slack: 권한표와 역할 명확성

Slack은 소유자/관리자, 멤버, 게스트의 권한 차이를 명시적인 표로 문서화한다. 어떤 권한이 기본 제공인지, 소유자 설정에 따라 달라지는지, 불가능한지를 구분한다. VIC도 역할 자체는 명확하므로, 제품 안에서 역할별로 할 수 있는 일을 더 잘 설명하면 된다.

출처: https://slack.com/help/articles/201314026-Permissions-by-role-in-Slack

적용 패턴:

* 역할 배지에 마우스를 올리거나 눌렀을 때 "내가 할 수 있는 것"을 짧게 보여준다.
* 사용자가 버튼이 없는 이유를 추측하게 하지 않는다.

### Figma: View/Edit/Admin 분리

Figma는 보기 권한, 편집 권한, 관리자 권한을 분리한다. 핵심 교훈은 "보기"와 "편집"이 단순히 버튼이 켜지고 꺼지는 차이가 아니라 서로 다른 사용 목적이라는 점이다. 보는 사람은 편집자가 되지 못한 사람이 아니라, 애초에 다른 화면이 필요한 사람이다.

출처: https://help.figma.com/hc/en-us/articles/360039970673-Team-permissions

적용 패턴:

* 시청자 미리보기, 매니저/작업자 화면, 소유자 화면, 개발자 화면을 서로 다른 작업 화면으로 다룬다.
* 편집할 수 없는 사람에게 소유자용 편집 화면을 꺼진 상태로 보여주지 않는다.

### Linear: 간결하고 집중된 관리 화면

Linear는 멤버/역할 관리를 설정 화면 아래에 묶고, 역할/상태별로 목록을 걸러볼 수 있게 한다. 전체 팀 관리와 일상 작업을 분리해, 일반 멤버가 관리 버튼에 방해받지 않게 한다.

출처: https://linear.app/docs/members-roles

적용 패턴:

* 팀/접근 제어는 하나의 "접근 관리" 또는 "팀 관리" 화면으로 묶는다.
* 일상 일정 운영과 계정/권한 관리를 분리한다.

### GitHub: predefined role과 최소 권한 라벨

GitHub은 owner, member, security manager, billing manager, app manager 같은 predefined organization role을 문서화한다. 모든 역할에 버튼 한 줄을 주는 것이 아니라, 역할 이름이 책임 범위를 설명하고 권한 그룹으로 매핑된다.

출처: https://docs.github.com/organizations/managing-peoples-access-to-your-organization-with-roles/permissions-of-predefined-organization-roles

적용 패턴:

* 역할 라벨이 책임을 말하게 한다. 예: "소유자: 일정 발행 & 접근 관리", "매니저: 업도움 & 꾸미기", "개발자: 시스템 유지보수".
* 역할 배지만 보여주고 실제 업무 범위를 설명하지 않는 상태를 피한다.

### Atlassian: 위임된 관리 역할

Atlassian은 하나의 강력한 관리자에게 모든 책임을 몰아주기보다 여러 관리 역할로 책임을 나누는 구조를 강조한다. VIC의 소유자, 개발자, 매니저, 작업자 구분과 잘 맞는다.

출처: https://support.atlassian.com/user-management/docs/what-are-the-different-types-of-admin-roles/

적용 패턴:

* "위임된 운영 작업"과 "소유권 작업"을 분리한다.
* 매니저/작업자는 일부만 꺼져 있는 소유자 관리 화면이 아니라, 자신에게 맡겨진 영역을 중심으로 본다.

### Notion: 멤버, 게스트, 워크스페이스 소유자

Notion은 멤버, 게스트, 소유자 같은 역할을 쉽게 구분한다. 협업 역할은 비개발자도 이해할 수 있는 말로 설명되어야 하고, "내가 무엇을 볼 수 있고 무엇을 할 수 있는지"와 바로 연결되어야 한다.

출처: https://www.notion.com/help/whos-who-in-a-workspace

적용 패턴:

* 매니저/작업자 권한을 쉬운 말로 설명한다. 예: "포스터를 꾸미고 업도움 링크를 고칠 수 있어요. 방송 일정 자체는 바꿀 수 없어요."
* 비공개 레이어 잠금 해제는 소유권이 아니라 임시 접근임을 분명히 한다.

### Material Design / 접근성: Disabled control은 설명이 필요하다

Material Design 접근성 가이드는 명확한 레이아웃, 뚜렷한 주요 버튼, 보조기술 지원을 강조한다. 권한 UI에서의 실무적 교훈은 "못 누르는 버튼"만으로 권한 차이를 설명하면 안 된다는 것이다.

출처: https://m2.material.io/design/usability/accessibility.html

적용 패턴:

* 역할상 영구적으로 불가능한 기능은 숨기거나, 별도 안내 화면으로 설명한다.
* 꺼진 버튼은 저장 중, 업로드 중, 필수 입력 누락처럼 잠깐 기다리면 해결되는 상황에 주로 사용한다.
* 권한이 없어서 할 수 없는 일은 못 누르는 버튼보다, 읽기 전용 화면과 짧은 설명으로 처리한다.

## 권장 역할 기반 UX 구조

### 1. 역할 인식형 Header

현재 문제:

* 역할 배지, 비공개 토글, 시청자 미리보기, 계정 변경이 같은 무게로 보인다.

권장:

* 왼쪽: 캘린더 제목과 현재 KST 월.
* 중앙 또는 보조 줄: "소유자 스튜디오", "매니저 꾸미기", "시청자 미리보기" 같은 현재 모드 표시.
* 오른쪽: 역할 배지와 계정 변경을 포함한 identity menu.
* 비공개 레이어 상태는 단순 버튼이 아니라 보안 상태 표시로 표현한다.

### 2. 기능별 Action Group

현재 문제:

* 태그 편집, 멤버 관리, 개발자 접속 현황, 꾸미기 버튼이 형제 버튼처럼 나열된다.

권장:

* **일정**: 일정 추가/수정, 공지 작성, 태그.
* **접근**: 비공개 레이어, 비밀번호, 멤버.
* **포스터**: 꾸미기, 내보내기, 스티커 이미지.
* **시스템**: 개발자 접속 현황, 진단.

### 3. 역할별 가장 중요한 버튼

역할별로 가장 먼저 보여줄 행동:

* 개발자: "진단 열기" 또는 "시스템 상태 확인". 일정 편집은 가능하지만, 화면에서 가장 중요한 버튼처럼 보일 필요는 없다.
* 소유자: "일정 추가" 또는 "선택 날짜 편집". 앱은 일정 발행 작업대처럼 느껴져야 한다.
* 매니저/작업자: "달력 꾸미기" 또는 "업도움 링크 수정". 도와주는 사람의 화면처럼 느껴져야 한다.
* 시청자: 스튜디오 버튼 없음. 포스터 탐색, 좋아요, 업도움 링크가 중심이다.

### 4. 매니저/작업자 일정 상세 보기

현재 문제:

* 편집 권한이 없는 사람이 소유자용 편집 화면의 꺼진 입력칸을 보게 될 수 있다.

권장:

* 매니저/작업자에게는 일정 상세 보기 화면을 제공한다.
* 일반 일정은 제목, 날짜, 상태, 링크를 확인만 하게 한다.
* 매니저에게만 업도움 일정에서 "기간/링크 수정"을 가장 먼저 보이는 버튼으로 둔다.
* 작업자에게는 업도움 수정 버튼을 보여주지 않고, 대신 제작에 필요한 참고 정보와 자료 업로드/꾸미기 흐름을 보여준다.
* 비공개 일정에는 "공개 전", "작업용" 같은 쉬운 표시를 붙인다. 소유자만 보는 일정은 절대 보이지 않아야 한다.

### 5. 개발자 점검 모드

현재 문제:

* 개발자 기능이 소유자 기능 옆에 있어 일반 편집자처럼 느껴진다.
* 현재 개발자는 시청자 화면 미리보기는 볼 수 있지만, 소유자 화면이나 매니저/작업자 화면이 실제로 어떻게 보이는지는 직접 계정을 바꾸거나 권한을 바꿔야 확인하기 쉽다.

권장:

* 별도 "개발자 점검" 패널을 둔다.
* 포함 정보:
  * 접속자 수,
  * 역할 분포,
  * 배포/빌드 정보,
  * 소유자 전용 일정은 제외된다는 짧은 안내.
* 파괴적이거나 권한에 민감한 행동은 명시적인 점검 그룹 안에 둔다.
* 개발자 전용으로 "역할별 화면 미리보기"를 추가한다.

역할별 화면 미리보기 구성:

* **시청자 화면 미리보기**: 현재처럼 공개 포스터와 공개 일정만 보인다. 편집/꾸미기/비공개 버튼은 보이지 않는다.
* **소유자 화면 미리보기**: 소유자가 보는 상단 버튼 배치, 일정 편집 흐름, 멤버/태그/비공개 관리 위치를 확인한다. 단, 실제 소유자 전용 비공개 일정 내용을 개발자에게 새로 보여주는 기능이 되어서는 안 된다.
* **매니저 화면 미리보기**: 방송 매니저가 보는 제한된 작업 화면을 확인한다. 일반 일정은 상세 보기만 가능하고, 업도움 일정에서는 기간/링크 수정 버튼이 가장 잘 보이는지 점검한다.
* **작업자 화면 미리보기**: 제작 협업자가 보는 화면을 확인한다. 작업용 일정, 참고 자료, 이미지 업로드, 포스터 꾸미기 흐름이 잘 보이는지 점검한다. 업도움 수정 버튼은 보이지 않아야 한다.

이 기능의 UX 원칙:

* 이 기능은 "권한을 빌려 쓰는 기능"이 아니라 "화면 모양을 점검하는 기능"이어야 한다.
* 실제 저장, 삭제, 멤버 변경, 비밀번호 변경 같은 행동은 미리보기 안에서 막는다.
* 미리보기 화면 상단에는 항상 현재 상태를 표시한다. 예: "개발자 점검 중: 매니저 화면으로 보는 중".
* 개발자가 미리보기를 켰다가 끄면 원래 개발자 화면으로 즉시 돌아와야 한다.
* 시청자/소유자/매니저/작업자 미리보기는 같은 위치에 모아두고, 버튼 이름은 쉬워야 한다. 예: "시청자처럼 보기", "소유자처럼 보기", "매니저처럼 보기", "작업자처럼 보기".

### 6. 소유자 발행 작업대

현재 문제:

* 소유자는 서로 다른 성격의 버튼을 비슷한 무게로 많이 본다.

권장:

* 소유자 첫 화면은 다음을 우선한다.
  * 현재 월,
  * 일정 추가/수정,
  * 비공개 상태,
  * 포스터 준비/내보내기 상태.
* 멤버 관리와 태그 관리는 관리 메뉴 또는 옆 패널로 묶는다.

### 7. 시청자 포스터 우선 경험

현재 문제:

* 시청자 화면에서 계정/로그인 버튼이 포스터보다 더 눈에 띌 수 있다.

권장:

* 시청자 UI는 포스터 중심을 유지한다.
* 로그인/계정 변경은 조용한 상단 코너 또는 메뉴에 둔다.
* 좋아요, 필터, 업도움 링크는 귀엽고 가볍게 유지한다.

## 우선순위별 권장사항

### P0: 보안 경계 유지

* 공개/시청자 화면에 비공개 정보를 노출하지 않는다.
* 매니저/작업자를 일정 편집 가능하게 만들지 않는다.
* 명시적인 제품 정책 변경 없이는 개발자가 소유자 전용 일정을 읽거나 만들 수 없게 유지한다.
* 어떤 권한도 client-only hide에 의존하지 않는다.

### P1: 상단 버튼 영역 재구성

* 현재의 한 줄 버튼 나열을 기능별 그룹으로 바꾼다.
* 계정/모드 버튼과 실제 작업 버튼을 분리한다.
* 역할별로 할 수 있는 일을 짧은 도움말로 제공한다.

### P1: 매니저/작업자에게 소유자용 편집 화면을 보여주지 않기

* 매니저와 작업자는 일정 상세 보기 화면을 본다.
* 매니저에게만 업도움 일정에서 기간/링크 수정 버튼을 크게 보여준다.
* 작업자는 업도움 수정 대신 작업용 일정 확인, 자료 업로드, 꾸미기 흐름을 중심으로 둔다.

### P1: 매니저와 작업자 권한 분리

* 매니저는 방송 운영 역할로 정의한다: 업도움 기간/링크 수정, 공개 전 일정 확인, 공지 초안 확인, 시청자 화면 점검.
* 작업자는 제작 협업 역할로 정의한다: 작업용 일정 확인, 의상/이미지/스티커 자료 업로드, 포스터 꾸미기, 제작 상태 표시.
* 작업자에게서 업도움 기간/링크 수정 권한은 제거한다.
* 두 역할의 배지 색상과 설명을 다르게 해서, 한눈에 다른 역할임을 알 수 있게 한다.

### P1: 비공개 레이어 상태 가독성 강화

* 상태 라벨을 쉬운 말로 둔다: 잠김, 비밀번호 필요, 비공개 일정 표시 중, 소유자 전용은 제외됨.
* 소유자가 비공개 레이어를 켰을 때는 더 강한 warning copy를 보여준다.
* 매니저/작업자에게는 소유자 전용 일정이 계속 숨겨진다는 점을 짧게 설명한다.

### P2: Admin Surface 개선

* 멤버 관리와 비밀번호 설정을 하나의 Access panel로 묶는다.
* standalone trusted-members page와 modal trusted-members 권한을 일관되게 맞춘다.

### P2: 개발자용 역할별 화면 미리보기 추가

* 개발자에게만 "시청자처럼 보기", "소유자처럼 보기", "매니저처럼 보기", "작업자처럼 보기" 버튼을 제공한다.
* 이 미리보기는 화면 점검용이어야 하며, 실제 권한 상승이나 데이터 변경 기능이 되면 안 된다.
* 미리보기 중에는 저장/삭제/멤버 변경/비밀번호 변경 같은 위험한 행동을 막는다.
* 매니저 미리보기에서는 일반 일정 상세 보기와 업도움 수정 버튼의 위치를 집중 점검한다.
* 작업자 미리보기에서는 작업용 일정, 자료 업로드, 꾸미기 흐름을 집중 점검하고 업도움 수정 버튼이 숨겨졌는지 확인한다.
* 소유자 미리보기에서는 소유자 화면의 버튼 배치와 관리 메뉴 위치를 점검하되, 개발자가 볼 수 없는 소유자 전용 일정 내용은 새로 노출하지 않는다.

### P2: 꾸미기 모드 역할별 정리

* 소유자/개발자: 스티커 도구 + 포스터 테마.
* 매니저: 스티커 도구 + 내보내기 + 업도움 기간/링크 수정, 테마 없음.
* 작업자: 스티커 도구 + 이미지 업로드 + 내보내기, 테마 없음, 업도움 수정 없음.
* 꾸미기 모드 안의 시청자 미리보기는 현재처럼 편집/내보내기 버튼을 잠시 숨기는 방향을 유지한다.

## 제안하는 향후 정보구조

### 개발자

* Header: Developer Mode, 현재 계정, 계정 변경.
* Primary zone: 시스템 진단.
* Secondary zones: 일정 유지보수, 접근 유지보수, 포스터 유지보수, 역할별 화면 미리보기.
* 짧은 안내: 소유자 전용 일정은 제외됨.

### 소유자

* Header: Owner Studio, 비공개 레이어 상태, 시청자 미리보기, 계정 메뉴.
* Primary zone: 일정 발행.
* Secondary zones: 접근/팀, 태그, 포스터 꾸미기.
* 비공개 상태 활성 시 warning-heavy 처리.

### 매니저

* Header: Manager Studio, 비공개 레이어 상태, 시청자 미리보기, 계정 메뉴.
* Primary zone: 업도움 운영.
* Secondary zone: 방송 링크 점검, 포스터 꾸미기.
* 일반 일정은 확인만 가능한 상세 보기.

### 작업자

* Header: Worker Studio, 비공개 레이어 상태, 시청자 미리보기, 계정 메뉴.
* Primary zone: 작업용 일정과 제작 자료.
* Secondary zone: 이미지 업로드, 스티커/포스터 꾸미기, 제작 상태 표시.
* 업도움 기간/링크는 확인만 가능하고 수정하지 않는다.

### 일반 시청자

* Header: 최소한의 포스터 identity와 월 이동.
* Primary zone: 공개 캘린더/포스터.
* Secondary interactions: 필터, heart, support link.
* 인증 컨트롤: 조용하고 보조적인 위치.

## 최종 전략 방향

VIC Schedule Studio는 역할을 "버튼이 있고 없는 권한표"로 보여주면 안 된다. 각 역할은 다른 일을 하는 사람으로 보여야 한다.

* 개발자는 시스템을 유지보수한다.
* 소유자는 일정을 발행한다.
* 매니저는 방송 운영과 업도움 흐름을 맡는다.
* 작업자는 제작 자료와 꾸미기 흐름을 맡는다.
* 시청자는 공개 달력을 즐기고 반응한다.

현재 코드의 권한 체계는 이미 이 방향을 대부분 지지한다. 이제 UI가 그 mental model을 더 분명하게 보여주면 된다.
