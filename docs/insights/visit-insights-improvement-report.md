## 1. 현재 상태 (세션 이벤트 모델로 교체 완료)

옛 모델(`visit_log` 일1회 + `presence_ping` 분 단위 버킷)을 **`visit_session` 한 테이블**로 통합했다.

- **한 줄 = 화면이 보이는 한 번의 방문.** 재진입하면 또 한 줄(여러 번 기록).
- 컬럼: `started_at`(진입) · `last_seen_at`(25초 하트비트) · `ended_at`(이탈, null이면 last_seen을 종료로).
- **체류 = `coalesce(ended_at, last_seen_at) − started_at` (초 단위).** 분 버킷의 반올림 한계 제거.
- **유령 방문 차단**: `content-ready` 신호(실제 달력 = PublicPoster/StudioShell 마운트) + `visible`일 때만 세션 시작 → 프리렌더·프리패치·백그라운드 로드(안 본 화면)는 0.
- 집계는 RPC 없이 JS에서(스트리머 1명 규모라 행을 받아 계산). 모든 그래프(일일 상세·월별 방문 패널·트렌드)가 같은 소스.
- 개인정보 비저장 유지: `account_hash`(단방향) · 역할 · 기기만.

### 현재 지표 정의
- **방문 수 / 역할별·기기별** = 순방문자(=`(날짜, 계정)` 고유, 계정당 하루 1). 재진입 세션은 합쳐짐.
- **시간대 동접 막대** = 세션 구간 초를 시간대별로 쪼개 `초/(3600×관측일수)` = 하루 평균 동접. `.vt-seg min-height`로 1초 방문도 한 조각.
- **관리자 방문 기록 / 접속 세션** = `role=owner` 세션을 세션별로(여러 줄), 시각·기기·체류(초)·계정(설정 owner 이메일 매칭 시 이메일, 아니면 `#N`).

## 2. 남은 문제점 (왜 더 손봐야 하나)

### P1. "방문 수"에 노이즈가 섞임 — **가장 큼**
프리렌더는 막았지만, **0~1초짜리 순간 진입**(실수 탭·바로 뒤로가기)이 아직 방문 1로 잡힌다.
세션 모델이라 이제 체류 초를 알므로, **최소 체류 미만은 방문에서 빼면** "방문 수"가 즉시 깔끔해진다.

### P2. 운영진 트래픽이 신호를 가림 — **체감상 가장 큼**
지금 그래프는 **개발자(본인) 테스트 트래픽이 지배**한다. 관리자(toryvac)도 운영 목적 접속이 잦다.
"진짜 시청자가 언제·얼마나 오나"가 운영진에 묻혀 안 보인다. → 운영진을 분리/제외해야 신호가 산다.

### P3. 지표가 한 종류뿐이라 의미가 좁음
"방문 수(순방문자)"만 있다. **재방문 여부·체류 시간·이탈**을 모르니 "왔다"는 알아도 "의미 있게 봤나"를 모른다.
세션 모델이라 이 지표들은 이제 추가 비용이 거의 없다.

### P4. 레거시 잔존 + 무한 증가
`visit_log`·`presence_ping` 테이블과 `presence_hourly/peak/active_days/owner_sessions` RPC가 **미사용으로 남아 있다**.
`visit_session`은 보존 정책 없이 계속 쌓인다(규모는 작지만 방치 시 누적).

## 3. 권장안 (이 프로젝트 기준)

스트리머 1명 · 운영진 소수 · 시청자 규모 작음 · KST · 개인정보 비저장 — 이 맥락에 맞춰 우선순위화.

### 지금 하기 (작고 안전, 효과 큼)

**R1. 방문에 '최소 체류' 컷 (P1)**
- 규칙: 세션 체류 `< 3초`는 **방문 수·역할별·기기별 reach 카운트에서 제외**. (동접 막대·세션 목록엔 그대로 남겨 "있긴 있었다"는 보존.)
- 구현: `MIN_MEANINGFUL_VISIT_MS = 3000` 상수를 만들고, `reachSlot` + `hours` 첫 진입 분포 + 멤버용 방문 하이라이트 집계에 같은 기준을 적용.
- 근거: 프리렌더 차단(visible 게이트) 위에 한 겹 더 — 실수 진입까지 걸러 "방문 수"가 사람 기준으로 정직해진다.

**R2. 운영진 분리 (P2)**
- 방식 A(추천): 방문 패널·일일 상세 헤드라인을 **"시청자 방문"** 기준으로, 운영진(owner·developer·manager·worker)은 별도 작은 줄로. 그래프는 "운영진 제외" 토글 1개.
- 방식 B(가벼움): 헤드라인 숫자만 시청자(viewer) 기준으로 바꾸고, 역할별 분해는 그대로(운영진도 색으로 보임).
- 구현: 집계에 `role === "viewer"` 필터 분기 + 토글 상태. 데이터는 그대로(역할이 행에 있으니 분기만).
- 근거: 본인·관리자 테스트가 시청자 신호를 가리는 게 지금 가장 거슬리는 지점.

**R3. 방문 횟수(세션 수) 같이 표기 (P3 일부)**
- 헤드라인 "N 방문(순방문자)" 옆에 "· 세션 M회"(재진입 포함). 둘 다 보이면 "여러 번 기록"의 의미가 안 헷갈린다.
- 구현: reach.total(이미 있음) + 세션 배열 length. 표시만 추가.

### 개발자 가시성 개선 (깔끔함 + 원인 파악)

**R4. 방문 품질 KPI**
- 헤드라인 아래 작은 KPI 줄: **의미 방문(3초 이상)** · **스쳐감(3초 미만)** · **바운스율(10초 미만)** · **평균 체류** · **총 체류**.
- 기본값은 시청자 기준. 운영진 포함 토글을 켜면 같은 KPI를 운영진 포함으로 재계산.
- 구현: 세션 배열에서 `durationMs`를 한 번 계산해 `meaningfulSessions`, `glanceSessions`, `bounceSessions`, `avgSeconds`, `totalSeconds`를 만든다.

**R5. 시청자/운영진 분리 배지**
- 방문 패널 상단: `시청자 N명 · 운영진 M명 · 세션 S회`.
- 개발자 테스트 트래픽 때문에 숫자가 부풀었는지 바로 보이게 한다.
- 구현: `role === "viewer"`와 `role !== "viewer"` 집계를 나눠 `VisitTrends`/`DayVisitDetail`에 보조 summary를 추가.

**R6. 한 문장 자동 인사이트**
- 예: "이번 달 시청자는 주로 20~22시에 방문했고, 평균 체류는 38초예요."
- 예: "스쳐감 비율이 45%라 방문 수보다 품질 지표를 같이 봐야 해요."
- 구현: 서버 집계 결과에서 top day/hour, avg duration, bounce rate, viewer/operator split을 보고 1~3개 문장 생성.

**R7. 요일 × 시간 히트맵**
- 7행(요일) × 24열(시간) 히트맵. 월 단위로 "시청자가 언제 자주 보는지"를 가장 빨리 보여준다.
- 데이터가 적으면 "데이터 적음" 상태를 표시하고 색 대비를 낮춘다.
- 구현: KST 기준 `weekdayOf(row.day)` + 세션 구간 시간 분해. 기본은 viewer only, 토글로 운영진 포함.

**R8. 날짜별 미니 히트맵**
- 월 방문 패널 안에 작은 달력형 히트맵. 방문 많은 날은 진하게, 클릭하면 일일 방문 상세 모달.
- 기존 일/주 막대보다 달력 일정과 머릿속 연결이 쉽다.
- 구현: `visits.days`를 그대로 쓰고 UI만 추가. 의미 방문 기준 적용.

**R9. 방문 ↔ 일정 연결 코멘트**
- 방문 많은 날에 공개 일정/휴뱅/일정 없음 상태를 같이 표시.
- 예: "방송 일정 있는 날 방문이 집중", "일정 없는 날 확인 방문 많음".
- 구현: 이미 인사이트에서 events를 조회하므로 date별 public content/rest 상태를 visit summary와 합친다. private 필드는 절대 포함하지 않는다.

**R10. 최근 세션 로그 (개발자 전용)**
- 하단 접이식 패널: 최근 20개 세션 `시각 · 역할 · 기기 · 체류 · 의미방문/스쳐감`.
- 원문 이메일은 저장/표시하지 않는다. owner 이메일 매칭 표시만 기존 원칙 유지.
- 구현: `visit_session` 최근순 조회. developer action에만 포함.

**R11. 데이터 건강 상태**
- `비콘 정상`, `end 유실 추정`, `평균 heartbeat 간격`, `오늘 세션 수`를 작은 상태줄로 표시.
- keepalive/end 유실이 있으면 방문 수가 이상해지는 원인을 개발자가 바로 알 수 있다.
- 구현: `ended_at is null`이면서 `last_seen_at`이 오래 지난 세션 비율, `last_seen_at-started_at` 패턴으로 추정. 원시 개인정보 없음.

### 곧 추가하면 좋음 (세션 모델이라 저비용)

**R12. 새 방문자 vs 재방문자** — `account_hash`가 날짜 넘어 유지되니, 그 달 처음 온 계정/다시 온 계정 분리. (account_hash 인덱스 1개 추가 권장.)
**R13. 월 최고 동시 접속** — 헤드라인에 "최고 N명 동접"(이미 peak 계산 있음, 월 최댓값만 노출).

### 큰 개편 때 묶기 (지금 급하지 않음)

**R14. 레거시 정리 (P4)** — `visit_log`·`presence_ping` 테이블 + 4개 RPC를 drop하는 마이그레이션. 충분히 안정화 확인 후.
**R15. 보존 정책** — `visit_session` 6개월 경과 행 정리(수동 SQL 또는 cron). 규모상 급하진 않으나 정해두면 깔끔.
**R16. 동접 인원 dedup** — 한 사람 2탭이면 동접 2로 잡힘. "동접 인원(계정 dedup)" vs "동접 세션" 구분 옵션. 규모상 후순위.

## 4. 추천 실행 순서

1. **R1(최소 체류 컷)** — `reachSlot`, `hours`, 멤버용 방문 하이라이트에 같은 기준 적용. 즉시 방문 수 정화.
2. **R2(운영진 분리)** — 기본은 시청자 기준, 토글로 운영진 포함. 진짜 시청자 신호 확보.
3. **R3(세션 수 병기)** — 순방문자와 재진입 세션 수를 같이 표시.
4. **R4(방문 품질 KPI)** — 의미 방문·스쳐감·바운스율·평균/총 체류를 상단에 추가.
5. **R5(시청자/운영진 분리 배지)** — `시청자 N명 · 운영진 M명 · 세션 S회`로 숫자 해석을 빠르게 만든다.
6. **R6(한 문장 자동 인사이트)** — 개발자가 그래프를 읽기 전에 핵심 변화를 먼저 보게 한다.
7. **R7(요일 × 시간 히트맵)** — 시간대 패턴 가시성 강화.
8. **R8(날짜별 미니 히트맵)** — 월 달력 감각으로 방문 많은 날을 찾게 한다.
9. **R9(방문 ↔ 일정 연결 코멘트)** — 방문 증가가 공개 일정/휴뱅/빈 날 중 무엇과 맞물렸는지 표시.
10. **R10(최근 세션 로그)** — 접이식 개발자 디버깅 패널. 이상 세션 확인용.
11. **R11(데이터 건강 상태)** — 비콘/end 유실 추정 표시. 집계 신뢰도 확인.
12. **R12·R13(재방문/최고 동접)** — KPI 보강. R12는 인덱스 추가 검토.
13. **R14·R15(레거시 정리/보존 정책)** — 안정화 확인 뒤 큰 정리로 묶기.
14. **R16(동접 계정 dedup)** — 필요성이 보이면 후순위로 진행.

> R1~R11은 데이터 모델 변경 없음(집계/표시 중심) → 마이그레이션 불필요, 위험 낮음.
> R12는 `account_hash` 조회 인덱스 1개 추가 권장(작은 마이그레이션).
> R14~R15는 안정화 전 drop/삭제 금지. 충분히 검증한 뒤 진행.

## 5. 리스크 / 주의

- **최소 체류 컷 값(3초)**: 너무 크면 짧지만 진짜인 방문이 빠진다. 3초 권장, 추후 조정 가능. 동접/세션 목록엔 남기므로 데이터 손실 아님(표시 기준만).
- **운영진 제외**: 기본값을 "제외"로 할지 "포함+토글"로 할지는 취향. 운영 점검용이면 토글로 둘 다 보게.
- **지표 기준 일관성**: `reachSlot`만 고치면 하이라이트 최고 시간대(`visits.hours`)가 과거 기준으로 남을 수 있다. 최소 체류 기준은 방문 관련 집계 전체에 같은 상수를 써야 한다.
- **개발자 로그 노출**: 최근 세션 로그는 developer 전용. viewer/member API에는 원시 방문 세션을 넣지 않는다.
- **방문 ↔ 일정 연결**: public schedule 상태만 연결한다. private/owner_private/work/embargo 정보는 코멘트 근거에 쓰지 않는다.
- **과거 데이터**: 세션 모델 전환(오늘)부터 누적. 지난달 그래프는 빈 게 정상.
- **개인정보 경계**: 계정 식별은 설정된 owner 이메일 매칭 한정 — 일반 시청자는 익명 유지(R2/R12도 이 원칙 유지).
